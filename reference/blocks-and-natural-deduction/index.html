    9. Blocks and natural deduction¶

    Every open proof/assume/case/let/pick/sandbox/expect pushes a new level onto the knowledge base. summary prints where the proof is: the open blocks with what opened them (; open: case A), the claims of open shows still to prove, the latest facts, and what could come next -- the same view that breakpoint and kurt -i show after stopping (§10), and that the playground and the editors use. list has a different job: it inspects declarations and facts retained from loaded theories. A block's own const/var declarations and any axioms used inside it disappear again once the block closes; only the formula the block's closing produces survives, on the parent level.

    Indentation drives block closing, identically whether you're reading a file or typing/pasting into the interactive shell. Dedenting — writing (or, in the shell, typing) a line less indented than the block's content — closes as many levels as the drop in indentation implies, applying whatever each level's closing rule is (impl-intro, forall-intro, ..., below). There is no separate "shell mode" for this: the interactive shell reads real leading whitespace exactly like a file does, so pasting file content into kurt -i behaves the same as running it as a file. To help with typing, the shell (at a terminal) starts each line with the indentation of the current block, one level (four spaces) deeper after a line that opens a block; a backspace over the indentation dedents by one level. The shell edits its lines itself, the same on macOS, Linux and Windows (no readline): ←/→, Home/End, Delete, Ctrl-A/E/K/U/W, the history with ↑/↓ (kept in ~/.kurt_history), Ctrl-R to search it, Tab (below), Ctrl-C drops the line, Ctrl-D on an empty line ends the shell; a long line wraps, and pasted lines are read one after the other. Not at a terminal (a pipe), it reads plain lines. Two keywords remain as optional alternatives to dedenting, and work identically in files and the shell: qed (§7 — still needs a real dedent, but also checks you're closing a proof) and break (§9.5 — needs no dedent at all, and is the only way to close a sandbox other than dedenting past it).

    Running a file itself already starts one level deep, inside an implicit sandbox (the same mechanism load uses, see §8.2); summary doesn't list that one.

    9.1 assume and case¶

    assume EXPR
    ...
(closes by dedenting, or `qed`/`break`)

    Opens a block that adds EXPR as a local axiom; for a conjunction A ∧ B, its parts are facts too, shown as derived lines 6a A, 6b B ("and-elim"; also for case and pick ... with A ∧ B). Closing it derives "impl-intro": whatever you proved last inside the block becomes EXPR implies <that>, on the parent level. If the last thing derived inside the block was literally false, closing additionally derives not EXPR via "not-intro" (both formulas are added). Inside the block, the free variables of EXPR are fixed: in assume P $x, $x is one arbitrary object, the same in every line of the block -- so P $x follows, but not P $y. Closing the block generalizes again: P $x implies ... holds for every $x. case closes like assume: a sequence of cases produces one EXPR implies <goal> for every branch. On the final explicit goal, Kurt looks for a flat or fact and exactly one such implication for every alternative. This shortcut is available only when the theory contains the general binary or-elim schema; it does not assign a built-in meaning to an operator merely named or. A dedicated case-elim certificate records that rule and the finite list, and the independent kernel checks both. This works for any number of alternatives without generating a schematic n-premise rule or searching a Cartesian product of facts. The disjunction itself must already be derivable/used, and every branch must have the same goal. Forgetting a branch, the disjunction fact, or the final explicit claim is the most common way a case proof silently doesn't finish — it fails with an ordinary "can not derive" on that final line, not a case-specific error.

    The running time of case (measured with scripts/bench_case.py, 2026-10-09, see dev/lab-notes.md): the final case-elim step itself is cheap and grows about quadratically with the number n of alternatives -- about 50 ms for n = 128 -- and it is always case-elim, never a combination the general search finds. The blocks are ordinary lines, though: if every block derives the goal with one of n rules that all have the goal as their conclusion, each block's search tries all of them, and the whole proof grows about cubically (about 0.2 s for n = 16, 5 s for n = 64, 40 s for n = 128 on a slow machine). For proofs with a handful of cases this doesn't matter. For very many cases, implications that name their case (A3 implies G, stated or proven) are fast: then case-elim uses them directly, without blocks (0.4 s for n = 128).

    9.2 let¶

    let SYMBOL             ; or a comma-separated list: let x, y, z
let CONDITION           ; e.g. let x>0
let SYMBOL with CONDITION   ; the same, naming the constant, e.g. let x with P(x)
    ...

    Introduces one or more brand-new constants (each must not already be a declared constant). A condition (let x>0) also uses the condition as a local axiom, in one step. Closing the block derives "forall-intro": the last thing proven inside becomes universally quantified over each new constant, in reverse declaration order, skipping any that turn out to be statement variables. let x with C is let C, with the constant named: it is rejected if C is about another symbol.

    let and pick take their conditions the same way, but they are opposite rules: let assumes the condition for an arbitrary x and gives "for all x" (∀-introduction); pick needs a known ∃ and gives a witness (∃-elimination). A pick without a matching ∃ says so, and suggests let.

    9.3 pick¶

    pick SYMBOL with FACT
pick FACT              ; the same, with the SYMBOL that FACT is about, e.g. pick c > 0
    ...

    Requires some already-known formula exists $x P in the theory such that substituting the new SYMBOL for $x in P gives exactly FACT -- or one that follows in one step, which Kurt then shows as a derived line 13a before the pick (e.g. from P(c) and a rule P($x) ⇒ ∃ y (Q y), pick b with Q(b) derives ∃ b (Q b) first). If found, it opens a block with SYMBOL as a new constant and FACT as a local axiom. Closing the block derives "exists-elim": the last formula proven inside must not mention SYMBOL (checked, and also not mention any other constant introduced on the block's own level) — with that check passed, it becomes the block's result on the parent level, without any reference to the witness.

    From an existential with a condition, exists $x > 0 P($x) (§4.4), FACT is the condition and the body for the witness: pick c with c > 0 ∧ P c -- as logic.kurt's "exists-cond-def" says, ∃ (sub $x $v %C) %P is ∃ $w ((sub $x $w %C) ∧ (sub $v $w %P)), so no detour through that rule is needed.

    SYMBOL must be a bare new-or-existing name, unlike let's otherwise similar let SYMBOL / let SYMBOL>0 (§9.2) — a picked witness can never carry an extra condition of its own the way a let-bound one can: let's condition becomes an assumption that gets quantified away when the block closes, but a picked witness is existential, so an unearned extra condition on it would just be an unproven fact about a specific value, not a sound derivation. pick x>0 with FACT is therefore rejected outright (EvalError) rather than silently accepted or silently ignored; the witness's only property comes from FACT itself. Without with, as in pick c > 0, the whole line is the FACT (as let c > 0 is the condition), and the witness is the one new symbol it is about.

    9.4 sandbox¶

    sandbox
    ...
(closes by dedenting, discarding everything inside -- or by `break`, immediately)

    A scratch block: everything inside is discarded by default, never merged into the surrounding theory, whether it closes by dedenting (§9's introduction) or by break (§9.5) right away. The end of the file closes a sandbox still open there like a dedent, discarding its content (sandbox ; 5 closed, its content is discarded).

    9.5 break¶

    break     ; discard the current block immediately, without proving anything

    break closes the current block right away, discarding it — no impl-intro, forall-intro, etc., nothing is added anywhere — without needing to dedent past it first. Works identically in a file or the interactive shell, and on any open block: it gives up the innermost open thing. Breaking out of a proof gives up only that attempt: the show it was trying to prove stays open, and a new proof can follow. Right after a show, or after the break of its proof, no block is open for the claim, so break withdraws the claim itself — break, break gives up a proof completely. A withdrawn claim is still to do: the file ends with "Proof almost checked" and the claim among its todos (it is not complete, for --json and the grader). A claim that is neither proved nor withdrawn is an error at the end of the file ("has no proof"). (Before 0.9, the first break withdrew the claim too.)

    break can't close the file's own implicit top-level scope (§8.2, §9's introduction) — there is no real, user-written block there to close, so it raises a clean error rather than doing anything to it.

    9.6 expect¶

    expect "KIND"
    ...
expect "KIND" "TEXT"
    ...

    Opens a block whose content is expected to raise an error of the given KIND (and, with TEXT, whose message contains TEXT). The kinds, each for one stage of reading and checking a line:

    kind when
    ScanError a symbol can't be scanned (an unknown character, a number with too many digits)
    ParseError the line can't be read: brackets, indentation, a chain's continuation, an incomplete expression
    EvalError the line is readable, but the statement isn't allowed: wrong arguments of a keyword, conflicting declarations, load problems, a claim that isn't a statement
    TypeError sorts, the arguments of sub, the variable or condition of a binder
    ProofError a claim can't be derived, a block can't close as it should

    (Every KurtException carries its .kind, see KurtException.KNOWN_KINDS in kurt.py.) If something inside the block raises exactly that kind, the whole block (including anything it did) is discarded and checking simply continues with the next statement, the same way break discards a sandbox. If the block closes normally with nothing having raised, that itself is now the failure (ExpectationError: this `expect "KIND"` block finished without raising a `KIND`); if something raises but of the wrong kind, that's also a failure, reported with both kinds shown.

    This exists so a proof file (or a lesson, see keywords/16-expect.kurt) can demonstrate a mistake and have Kurt itself confirm it still fails the expected way, rather than relying on a comment nobody re-checks, or on a separate test harness matching exact (and therefore fragile — see dev/todo-claude.md, in git history) error text.

    The expected error may come from anywhere inside the block: from a statement directly inside it, from inside a nested block (assume, proof, another expect, ...), or while such a nested block closes (a failing qed, or the dedent that closes a let/pick/proof). In the last case the line that triggered the dedent is already outside the expect block, so it is still evaluated afterwards. Any lines of the block after the one that raised the error are skipped. Since the content of an expect block is always discarded, use is allowed inside it (see §6.2). A second string is a text that the error message must contain: expect "ProofError" "can not derive" (a string can't contain "). A break inside expect closes the expect block itself; an error that only a whole file can make (a proof still unfinished at its end, a show without a proof, break at its top level, ...) is checked by expect around a load of such a file (see tests/how-to-write-test-proofs.md).
