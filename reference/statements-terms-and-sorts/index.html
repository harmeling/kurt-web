    5. Statements, terms and sorts¶

    5.1 Statements and terms: prop¶

    Kurt has two categories of expressions: statements, what is proved, assumed and combined with ∧ ∨ ¬ ⇒ ⇔ ∀ ∃, and terms, the objects -- any and the sorts below it (§5.2), which form a DAG (field ⊂ ring and field ⊂ ordered is fine; where two sorts meet, the meet must be one sort). prop declares which places take statements:

    prop P, Q              ; P and Q are statements (propositional constants)
prop even 0            ; `even n` is a statement: the result place 0
prop ∧ 0 1 2           ; `∧` takes two statements and is one
prop = 0               ; `a = b` is a statement; its places 1 and 2 are terms

    Position 0 is the result, 1, 2, ... the arguments; prop P is short for prop P 0. Every place is a statement place or a term place: a place prop doesn't name is a term place.

    A statement is no object (decided 2026-10-20): a statement at a term place is a type error -- c = (A ∧ B), A ∈ M, f(A ∨ B) -- and so is a term at a statement place. Statements are compared with ⇔, not =. This is what the search and the kernel always did (no step puts a statement in for a term variable), and what the Lean export says (statements are Prop, terms Obj). Truth values as objects (a function into {true, false}, a Boolean algebra) are terms of a sort of their own (sort truth), never statements.

    prop is no sort: sort prop and sort any prop are refused, sort doesn't list it, no term fits a statement place.

    Statement variables. %A is a statement variable, by its sigil -- as $x is a term variable: in propositional logic, the propositional variable; in a rule of first-order logic it may contain the rule's term variables (∀ $x %A with sub $x $t %A). var p with prop p is the same with a plain name (§3.2). A statement variable is schematic: free in a use or a show, it says "for every statement" -- use false implies %A, show %A ∨ ¬%A -- and the search puts any statement in for it. Binders range over terms (decided 2026-10-20): ∀ p (p ∨ ¬p) with a statement p, and ∀ %A ..., are type errors -- nothing is lost, the schema says the same, and no file needed a statement bound inside a formula (proofs/soundness/binders-range-over-terms.kurt). So let, the introduction of ∀, fixes a term only: a proof about %A needs no let -- the claim's %A is one statement throughout the proof, an assume holds it fixed (proofs/soundness/let-fixes-a-term.kurt).

    First use. A new operator applied to statements gets those places at its first use, and that is final, like the first sorted use of §5.2 (infix xor 20 20, then A xor B: xor takes two statements, c xor d with terms is then a type error); a new constant used as a statement becomes one. Kurt prints the declaration it inferred, for example prop P 0 ; added statement places, next to const P ; added constant. Use explicit prop declarations where stable vocabulary and early typo detection matter; --strict additionally rejects undeclared symbols.

    Only use/show/bare top-level claims are required to be statements overall (the error is "must be a statement"); a binder's body is what the binder says -- a statement for ∀, ∃ and {x ∈ A | F}, a term for sum.

    5.2 Optional user sorts¶

    General sorts are optional. A theory that declares none has only the two categories of §5.1, statements and terms (all of sort any).

    Declare any additional categories a theory needs:

    sort nat, vec
nat a, b
vec v, w

    Each new sort name becomes a declaration keyword with the same positional notation as prop:

    nat + 0 1 2            ; result and both arguments are natural numbers
prop < 0               ; the result is a statement
nat < 1 2              ; both arguments are natural numbers
vec · 0 2              ; vector result and second argument
nat · 1                ; natural-number first argument

    A convention of the theories, not a rule of the language: sorts are lowercase, sets are capitalized. real x says what kind of thing x is (a sort, syntax); x ∈ Real is a fact about x (a set, an object a fact can be about). The number sort is real (objects.kurt, real ⊂ set; Kurt computes exactly with the rationals among them), the sets of numbers are Nat, Int, Rat, Real (ℕ, ℤ, ℚ, ℝ).

    All sorts are inhabited (a model has at least one object of each, doc/kurt-spec.md §2.2): a file that declares a sort and names no object of it -- no constant of the sort or of a smaller one, no numeral -- gets a warning at its end ("the sort vec ... has no constant in this file"), since it assumes one.

    Position 0 is the result; positions 1, 2, ... are arguments. A symbol without positions is short for result position 0, so nat a means nat a 0. Unmentioned positions remain unconstrained. Different sorts may describe different positions of one operator, but one position cannot have two sorts. A sorted variable remains constrained when Kurt instantiates it as part of a rule, including after the rule crosses a load; proof search and the certificate kernel both check the constraint.

    Subsorts¶

    An item of a sort line is one name, or a chain of names read like chain (§4.6): sort set real int declares the names that are new and makes int ⊂ real ⊂ set; commas separate items, sort set real, set vec gives set two subsorts. The relation is a DAG with its transitive closure (int ⊂ set too); a cycle is an error, also one that a load would make. The line says what it declared:

    sort set real int                          ; real ⊂ set, int ⊂ real

    A value of a sort fits a position or a variable of the same sort or of a bigger one: a number fits where a set is required (3 ∈ {3}), a set doesn't fit where a number is ({1, 2} + 0 is a type error). A sorted rule stays strict: a rule about the numbers never applies to a set, and one about the sets applies to a number. A sort name where a symbol is declared is refused with a hint (set real -- "a subsort is declared with sort set real"). sort alone lists the sorts and the subsorts with where they were declared.

    any is the sort of all objects, every sort is below it, and every symbol without a sort is over all objects: a variable, a bound variable and a block's constant, inside a formula as at its top (∀ x (x ∈ A ⇔ x ∈ B) is about all objects wherever it is written, so it meets "extensionality"), and a constant until a use gives it a sort. set and real (objects.kurt) are restrictions below any, real ⊂ set: a binder over the sets is one over fewer objects, like one over the numbers. set.kurt declares the places that are sets (set ∈ 2, set ⊂ 1 2, set ∪ 0 1 2, ...) and has no default: an element (the left of ∈, an element of {a, b}, the variable of a set-builder, a component of a pair) is any object.

    A fact gives no sort: x ∈ Nat says nothing about the sort of x (sorts are syntax, facts are semantics). ∀ x ∈ Nat ranges over the numbers where x is a number by its places (x + 1) or by default real; natural.kurt's induction applies to it only then, so a proof about numbers writes default real. There, ∀ n (n ∈ A ⇔ n ∈ B) is about the numbers only and doesn't meet "extensionality"; for sets of numbers natural.kurt has "ext-real": (∀ n (n ∈ A ⇔ n ∈ B)) ∧ A ⊂ Real ∧ B ⊂ Real ⇒ A = B, with the set Real of all numbers ("real-all": every number is in it) and Nat ⊂ Real, Int ⊂ Real, Rat ⊂ Real -- rules with proofs in Lean, not a link between sorts and sets (proofs/natural-numbers/sets-of-numbers-are-equal.kurt). ℕ, ℤ, ℚ, ℝ (typed \N, \Z, \Q, \R) are aliases of Nat, Int, Rat, Real. The elements of a set written by its elements ({1, 2}, {0, 2, ...}) have the sort of the elements. A polymorphic rule writes its bound variable $$x (logic.kurt: ∀ $$x %A ⇒ sub $$x $a %A): it is used for a binder over any sort, and the checker verifies that $$x occurs only in its binder, in subs and as a side of =.

    Inference and default¶

    A symbol without a declared sort takes the sort of its first sorted use, in every file: with real + 0 1 2, const x and then x + 0 = x make x a number; x ∈ A makes A a set. The line that gives a symbol its sort says so, like an inferred prop signature:

    7  x + 0 = x                     ; by add-identity
   real x                         ; sort inferred

    info x shows the sort and how it came (real x 0 ; level 1, f.kurt:7 (inferred)), and so does the hover of the line in an editor. = is polymorphic: it gives no sort.

    Where a use also takes smaller sorts -- the left of ∈ takes any set, and a number fits -- the default of the file decides, if it fits; without one, the position's own sort (x ⊂ A: a set). The default decides only at an element (the left of ∈, an element of {a, b}), not at a set: in $a ∈ $A, $A stays a set. Before its first sorted use (x = y: = gives no sort) a symbol has none: it is any object.

    The first sorted use is final. No later line changes the sort of a symbol: x ⊂ A makes x a set, and a later x + 1 is a type error, also though a number is a set. To use it as a number, declare it before its first use (real x); a number fits wherever a set is required. The message says both places and what to declare:

    TypeError: `x` has the sort `set` (inferred at line 3), but here it is used as `real` -- the first
sorted use decides; to make it a `real`, declare `real x` before that use

    A fact gives no sort -- b ∈ Nat doesn't make b a number -- and the message says that too, when such a fact is known. A declared sort, the sort of a defined symbol (def c = R: the sort of R), the sort of a witness (pick w with ...: the sort of the existential's variable) and that of a symbol of a loaded file are final as well.

    default SORT (only after sort SORT; not prop; at the top of a file, not inside a block): from this line on, every $ variable, operator position, bound variable and new constant of this file without a declared or inferred sort gets SORT -- an operator's positions at its first use after the line, except a statement place, and a binder's variable with the binder (sum i (0, n) i: i a number). The last default counts, from its line on. It doesn't cross load, but the sorts it gave to the file's symbols do, as sorts do. default alone names the one in force. default any is the same as none: a symbol without a sort is any object anyway, and a constant gets its sort at its first sorted use. numbers.kurt, natural.kurt, integer.kurt, rational.kurt and the analysis theories have default real; set.kurt, group.kurt, field.kurt and vectorspace.kurt have none (their symbols are over all objects). A student's file has none, unless it wants one: after default real, every symbol that has no other sort is a number. "No other sort" includes what the line itself says: in use A = {n ∈ Nat | n > 2} the other side of = is a set, so a new A is a set there, not a number (proofs/soundness/default-yields-to-equality.kurt).

    Variables ($x, a var, a bound variable) get their sorts per formula, from all their places in it -- the same formula always reads the same; a constant of a block keeps the sort it got there when the block closes: let x, then x + 1 > x, gives ∀ x (...) over the numbers, also if the last line doesn't mention arithmetic (the kernel checks it, doc/kurt-kernel.md).

    A checker sort versus an object-level carrier¶

    sort nat and const Nat express different design choices. A sort belongs to Kurt's checker:

    sort nat
nat n

    This constrains where n may occur, but nat is not a term, set, or proposition. In contrast, natural.kurt declares Nat as an object-level constant (of sort set). Together with membership from set.kurt, $n ∈ Nat is an ordinary mathematical proposition that can occur in assumptions and theorems. The two don't meet: n ∈ Nat gives n no sort, and a checker declaration real n does not prove n ∈ Nat.

    A sort property does not decide whether a symbol is a constant or variable, just as prop, infix, and arity do not. Write var a or const a when the role matters; otherwise the usual first-use rule still applies. A declared sort name is reserved and cannot also be a term symbol or Kurt keyword. Sort declarations and signatures must precede the symbol's first use.

    For a binding operator, the declared sort of its first position also types a fresh bound name in the body. sub x a A preserves the result sort of A; if x has a sort, its replacement a must have it. A rule of logic.kurt, written with $$x, is used for a binder of any sort (∀ x over the numbers): its bound variable stands for the binder's, and each sub checks the sort of what it puts in -- all $$ binders of one use over the same sort, and only a rule whose $$ variable occurs nowhere else but in subs, = and where it is bound; "extensionality" ($c in its body) is about all elements, and for the numbers alone it would make ∅ = {∅} (doc/kurt-soundness.md §8.41-§8.42).

    Order-sorted logic, and why it is sound¶

    These sorts make Kurt an order-sorted logic: a partial order of sorts with any on top, values that fit wherever a bigger sort is required, and rules for every sort at once ($$x). What makes that sound -- every variable has a sort, substitution respects it, binders are the same only over the same sort, one sort per use of a polymorphic rule, $$x only where the sort doesn't matter, non-empty sorts, a meet for every two uses of a symbol -- and where each is enforced (by the search and again by the kernel) and tested (proofs/soundness/, Lean) is in doc/kurt-soundness.md §10. Restriction (∀ x:set P to ∀ y:real P) and widening (∃ x:real P to ∃ x:set P) are no rules: let with "forall-elim" and pick with "exists-intro" do them (proofs/restriction-and-widening.kurt).

    Every top-level sort declaration crosses load as part of the theory's public vocabulary, even if no exported fact uses it yet; so do the subsorts. Sort signatures cross with the symbols that exported facts need (not those of $ variables: their sorts are in the facts), and all declarations retain their source locations. A sort is declared by one file only (objects.kurt declares set and real for set.kurt and numbers.kurt, which both load it). Inspect them with:

    sort                     ; prop plus every user sort, and the subsorts
nat                      ; every nat signature
list sort lambda         ; sorts retained from lambda.kurt
list term lambda         ; term signatures retained from lambda.kurt

    Generic equality deliberately remains polymorphic: prop = 0 constrains its result but leaves its two operands unsorted. A theory may add more specific operators when it wants stronger checking.

    Overloading. An operator may have a second signature on the same places for a sort that fits the first one (real ⊂ complex): + - * / ^ of numbers.kurt have one on real and, after load complex, one on complex (complex.kurt). A signature is of one sort at all its places (complex ^ 0 1 2: the exponent of z ^ 2 is a complex number too), so abs : complex -> real can't be one -- complex.kurt has cabs. A term gets its least sort from its syntax: 1 + 2 and x + y for reals are real, z + 1 with a complex z is complex, so (1 + 2) < 3 is well-sorted and z < 3 a type error (< is on real). A law of the reals is not used for a complex value (z + 1 doesn't fit its real variable); complex.kurt has the same laws for complex. A new constant at a place of an overloaded operator is inferred to be the smallest sort (x + 1: a real); a complex one is declared (complex z). Only a theory of Kurt can add a signature to an operator of another file; a signature for unrelated sorts (real, vec) is not possible yet (decision 19 of dev/todo-sorts.md, stage 2); doc/kurt-kernel.md §8.5 has the soundness argument.

    5.3 Operators are no objects; functions as values are mappings¶

    An operator -- a function symbol (arity f 1), +, ∪, a predicate -- is no object: it is applied, never compared, quantified over, or passed where a term is required. f = g for two function symbols, P(f), a ∀ x instantiated with f: each is a type error ("f is an operator without its arguments -- an operator is no object; a function as a value is a mapping"). The one exception is an operator parameter, a place where a defined predicate takes an operator: group.kurt defines group($G, (∘), $e, (ι)) with the operator variables ∘ and ι, so group(R, (+), 0, (-)) passes + and - there -- a schema, which the definition unfolds into first-order formulas about + and -.

    A function that is a value is a mapping of set.kurt: a set of pairs, f ∈ A → B, applied by juxtaposition, f a. Mappings are objects: they are compared (two mappings from A that agree on A are equal, "function-extensionality"), they are elements of sets, a quantifier ranges over them. Like every fact, f ∈ A → B gives f no sort; declare set f (proofs/set-theory/function-extensionality.kurt):

    set f, g
use f ∈ (A → B)
use g ∈ (A → B)
use ∀ a ∈ A (f a = g a)
f ∈ (A → B) ∧ g ∈ (A → B) ∧ ∀ a ∈ A (f a = g a)
f = g                                 ; by "function-extensionality"

    Why (decided 2026-10-20). Until then an operator was also a value: f = g was accepted and rewrote f c to g c, P(f) was a formula, and ∀ k included the operators. That has no first-order meaning: the soundness argument (doc/kurt-kernel.md §8) models an operator as a total function, not as an object, and in the model of the Lean export -- ZF sets -- ∪ or a field's + as an object would be the graph of an operation on all sets, a proper class. A bare operator also had the sort of its result, so with real f 0 1 the function f counted as a number (f + 0 = f was well-sorted, and a fact about all numbers applied to f). Making operators first-class objects would have meant an applicative semantics, a sort of its own for operator values and a Lean model with objects that are no sets -- higher-order logic through the back door. Kurt stays first-order: operators are applied, mappings are the functions one can talk about, and the operator parameters of structures are schemas. The search (bare_operator_for), the kernel (k_has_kind) and the type check (bare_operator_as_value, operator_parameters) agree on it.
