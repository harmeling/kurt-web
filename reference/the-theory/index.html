    6. The theory: making and using claims¶

    The theory is the accumulated list of Formulas (axioms, definitions, and proven facts) currently in scope. Kurt is a single-pass checker: each top-level statement is scanned, parsed, type-checked, and evaluated in order, and generally either succeeds (and is appended to the theory) or raises an exception (and, in a file, stops checking).

    6.1 Bare claims¶

    A line that's just an expression (no leading keyword) is a claim: Kurt tries to derive it from the current theory and, if it succeeds, adds it to the theory. If it's a conjunction, each conjunct may be derived separately and then combined via "and-intro" (this, "impl-elim"/modus-ponens against every formula currently in scope, and "top-intro" for the literal symbol true are the primitive rules hard-coded in Python; the engine also uses an iff fact as an implication in both directions, computes "by calc", closes case blocks "by case-elim", and generates the "chain-trans-I-J" rules of a chain -- see §8.1). Derivation is a single hop: given A, A implies B, and B implies C all separately in the theory, deriving C in one step is not automatic — you must first derive B as its own line.

    When a claim fails, Kurt says that no one-step derivation was found and shows at most three relevant rules whose conclusions match the goal, together with their missing premises. These are bounded search diagnostics, not proof certificates and not a claim that the formula is false. The structured form is available as CheckResult.failure, in the failing JSON event, and in the LSP diagnostic's data.failure field.

    Where the claim and every fact of the context are propositional, Kurt also looks for a counterexample by truth table: an assignment of the atoms that makes every fact true and the claim false. If there is one, the explanation ends with a line like

    a counterexample: with `A` false, `B` false and `C` true, every fact holds but the claim doesn't -- it does not follow from these facts

    (here for the claim B from A ⇒ B and A ∨ C), and failure.counterexample.assignment has the assignment, {"A": false, "B": false, "C": true}. Unlike the missing premises, this is a statement about the claim itself: no proof of any length derives it from these facts. The connectives with a truth table are ∧, ∨, ¬, ⇒, ⇔, true and false; any other statement (A, P a, x ∈ B) is an atom whose truth is free, so a fact with a quantifier or an object variable ($x) -- every rule of logic.kurt, equality.kurt and the theories on them has one -- or with a statement under an operator the table doesn't know (A ⇐ B) means the facts can't be evaluated, and nothing is said, whatever the atoms: in practice, counterexamples come in propositional contexts (the core, propositional.kurt, prop A, B). The rules of propositional.kurt, which are schemas over statements (%A ∧ %B ⇒ %A), hold in every row. The table has at most 12 atoms and is given a fraction of a second; beyond that, nothing is said either. When no counterexample is reported, nothing follows from that: the claim may well hold, in more steps than one. The assignment is checked again, with an evaluator separate from the one that searched for it, before it is reported; the check runs only after a line has failed, so it never changes what Kurt accepts.

    Running time. Since a claim is one step, its search is bounded: Kurt tries the facts, then the rules whose conclusion can match the claim (found by an index on the top-level operator of the conclusion), and for each rule the facts for its premises. What makes a line slow is therefore not the length of a proof but how many rules could have concluded the claim, times the size of the theory their premises are searched in: a theory with many rules for the same conclusion (or rules whose conclusion is a mere schema, like "equal-elim") makes every line that reaches them slower. The lessons and most proofs of this repository check in a second or two, the larger theories (natural.kurt, field.kurt) in several seconds; scripts/bench.py measures a set of representative files (before and after a change to the search; dev/dev-notes.md, "speed", has the history). A .kurtc file (§1) makes a file that is checked again much faster, since each step first tries its stored certificate.

    One exception, for rewriting: a rewriting step (a chain X = A / = B, or a claim that changes one place of a recent fact) may use a rule with conditions, e.g. $a ∈ K ⇒ 1 · $a = $a, if the conditions are facts. Kurt then derives the instance (1 · b = b, with the fact b ∈ K) as a step of its own, shown as line 17a before line 17, and rewrites with it. Both steps have their certificates, which the kernel checks.

    The first line of a chain, L = R, is rewritten like the later ones, as if L = L (equal-intro) were the line before it: a ∘ e = a ∘ (inv(a) ∘ a) follows by "left-inverse" inside the term. And a line that changes up to four places at once, x + y = 0 + 0 from x = 0 and y = 0, is checked place by place: Kurt adds the lines in between as steps of their own (17a, 17b, ...), each one rewrite with its certificate. Both are tried only when nothing else gives the line.

    A rewrite may also change a part of the arguments of a flat operator, where flattening removed the node: in x·x + x + (- x) + (- 1), the rule $c + (- $c) = 0 rewrites x + (- x) (for a sym operator any part, otherwise only arguments next to each other: b · l · a to b · a · l). The place is found by comparing the line with the one before; the kernel flattens after substituting, as always.

    A claim that's structurally identical to the last thing already in the theory is logged as a restatement of it (by 2), without being added again. Each checked line is logged with the short form of its certificate (§6.5): the rule, applied to the facts it was used with -- by 13(14) is the (unlabelled) implication of line 13 applied to the fact of line 14, by equal-elim(11, 10) the rule "equal-elim" applied to lines 11 and 10, by 3 an instance of the fact of line 3, by and-intro(12a, 12b) a conjunction checked conjunct by conjunct. The result of a block that closes is numbered by the lines of the block, from the line that opened it to its last one, ; 15-23 by impl-intro (the assume at line 15, the block to line 23; with false at its end also ; 15-23 by not-intro), and a step that uses it names them: by case-elim(14, 15-23, 24-30). A cited line that is only admitted (todo, §6.3) says so: by and-intro(5, 6 (todo)). In front of a line of the file, Kurt prints its number, and the reason goes without it; a derived line has no number in front, its number is in the reason (; 12a by and-elim(12), ; 15-23 by impl-intro) -- kurt --no-line-numbers prints every number in the reason instead (; 4 by 2(3)). If the line has a comment of its own, the comment stays on the line, and the reason goes on the next line:

       4  B                                         ; modus ponens
                                                ; by 2(3)

    Labelling (§6.2) isn't specific to use/def — it's the same mechanism for every statement, keyworded or not, since they're all parsed through the same check_expr_label. A bare claim can be labelled, and marked local, exactly like an axiom can:

    use P implies Q
use P
Q  "derived-q"        ; a label on a bare, derived claim works too

    and this is what actually decides whether Q is exported when this file is loaded elsewhere (§8.2) — not whether it came from use or was derived as a bare claim.

    6.2 How to define things: def and use¶

    use EXPR              ; use EXPR "label"
use EXPR local "label"
def SYMBOL = EXPR
def SYMBOL iff EXPR

    There are two ways to write what mathematicians call a definition, depending on what kind of definition it is:

    • Use def for a conservative definitional extension: one fresh name is introduced as an abbreviation for a term or property already expressible in the language.
    • Use use for any broader defining principle, including a recursive, conditional, implicit, or characterizing definition. Such a statement is an axiom to Kurt, even when its label ends in -def.

    For example, these only add names for expressions the language already has:

    def four = 2 + 2
def square($x) = $x * $x
def even($n) iff exists $k ($k in Nat and $n = 2 * $k)

    Every accepted def is intended to be eliminable: expand the new symbol by its definition and the theory says nothing new in its old vocabulary. Thus def expands the language without increasing the mathematical strength of the theory. Kurt checks the syntactic conditions described below; the soundness of that check is part of Kurt's trusted definition boundary.

    A recursive definition is not such a simple abbreviation. Kurt currently has no termination, constructor, or coverage checker with which to justify one as conservative, so write its equations as explicit defining axioms:

    const fact
use fact(0) = 1                                      "factorial-zero"
use $n in Nat implies fact($n + 1) = ($n + 1) * fact($n)  "factorial-step"

    The same applies when characterizing an existing object or notation, or when the defining equation has conditions. use is the honest spelling: Kurt accepts the formula without proving existence, uniqueness, termination, consistency, or conservativity. Such defining axioms can add genuine mathematical strength and can make a theory inconsistent if they are wrong. Their necessary domain conditions therefore belong in the formula.

    use adds EXPR to the theory as an axiom — accepted without proof. It is only allowed at the top level of a file, or inside a sandbox or expect (whose content is discarded anyway) — not inside a proof, assume, case, let or pick, where the result would look proven although it relies on the axiom (e.g. assume A with use B inside would give A implies B "by impl-intro"). State axioms before the proof, or use todo (§6.3) for a step you want to leave open. The same holds for chain (it generates axioms), load, inline, and every grammar declaration (infix, prefix, postfix, brackets, arity, binder, flat, sym, alias, sort): not inside a proof, assume, case, let or pick (EvalError: \inline` is not allowed inside `assume`), but in asandboxorexpect-- declare them before the proof. For the grammar declarations this isn't only about looking proven: a notation used by a formula that survives the block gets locked in for good wherever that formula is visible, so it was never actually scoped to the block in the first place ([§11.2](known-gaps.md#sec-11-2)). Adef` is allowed in a block: it is local to the block (see below).

    An optional trailing string labels a use. The label is shown on the use output line and on later references and error messages instead of a bare line number. When the axiom contains declared named variables, normal output also shows the stored schematic form in a ; schema: comment. For example:

    var x, y, ∘
infix ∘ 70 70
use x ∘ y = y ∘ x "comm"
; schema: $x $op $y = $y $op $x

    Statement variables use % names, term and function variables use $ names, and a symbolic operator variable gets a readable name such as $op. These generated names are stable display names; they are not declarations and are not written into saved Kurt source. format source continues to show the input line exactly, without the generated annotation. Formula listings (use with no arguments, theory, and list theory FILE) repeat the annotation. The label also controls whether EXPR is exported when this file is loaded elsewhere — see §8.2 — unless it's marked local, in which case the label is still used for display but the fact stays private to this file. show/proof/qed (§7) and def follow the exact same rule: def's label controls whether the symbol it introduces is (indirectly) exportable, and a proved theorem's show label carries forward to the final proved formula.

    Since a bare %/$ schema variable in a use/def axiom means "for any value of this symbol", it's easy to accidentally write an axiom that's far stronger than intended — e.g. use %A literally asserts "every proposition is true", and use %A implies P (with %A not reappearing anywhere in P) makes P derivable completely unconditionally, since %A freely unifies with anything. Kurt prints a Warning: to stderr (not an error — such an axiom is occasionally written on purpose) when a use/def matches one of these obvious shapes; see doc/kurt-soundness.md §6 for the full explanation and its limits (it only catches a few syntactic patterns, not every equivalent phrasing).

    Operationally, def is use specialised to introducing exactly one brand-new constant via an equation (=) or equivalence (iff) — the only two top-level operators def accepts. Exactly one new symbol must appear on the left-hand side (e.g. def x = 18, or def $a ∩ $b = { $c ∈ $a | $c ∈ $b } — infix notation puts the new operator between its arguments). The left-hand side must be the new symbol itself or that symbol applied to distinct variables, possibly curried. Defining a new symbol as an argument of an existing operator is not supported: write def injective($f) iff ..., not def $f is injective iff ....

    The new symbol must not occur on its own right-hand side, even through an alias. It must not already have semantic declarations such as calc, flat, sym, chain, or binder. Comma-separated definitions are checked left to right: def p iff true, q iff p is allowed, but defining the same symbol twice, or defining a symbol already used by an earlier entry, is not. A rejected batch adds no definitions or declarations.

    On the right-hand side, a symbol that wasn't declared is introduced as on any line (§3.4: a constant, reported as const g ; added constant; an error with --strict): def r = g b with a new g only names the term g b, whatever g is, so the definition stays conservative. A declared operator isn't new even before its first use, e.g. the comma of def q = ⟨b, b⟩. The right-hand side has no variables besides those of the left-hand side. A definition is safe (it can't make the theory contradictory) only if = and iff have their usual meaning, so def requires them to come from the theories that come with Kurt: load equality (for =) or load propositional (for iff) first — an iff or = declared some other way is rejected. Once those checks pass, the defining equation is stored as a fact and can be used for rewriting and inference like a use axiom. Its provenance remains def, because the reason it is safe to admit is different: the checked extension is conservative rather than an additional mathematical assumption. Both use and def, called with no arguments, print everything used/defined so far.

    def inside a block. A def may also be written inside a proof, assume, case, let or pick (since 2026-10-27; also with --strict, it is conservative by its form). There it is local to the block: the new symbol is a constant of the block, and the symbol and its defining fact are gone when the block closes. The right side may mention the block's own constants -- a name for a term about the let constant or the pick witness:

    show ∀ $a ∃ x (x > $a * $a)
proof
    let a
        def w = a * a + 1             ; a name for a term about `a`
        0 < 1
        0 + a * a < 1 + a * a
        a * a < a * a + 1
        a * a < w
        ∃ x (x > a * a)               ; `w` is the witness
qed

    A local function, def sq($y) = $y * $y + 3, works the same way (its parameters are variables, as at the top level). The result of the block -- its last line, made into A ⇒ L, ∀ x L, or L itself after pick -- must not mention the defined symbol (ProofError: \w` is defined in this block (line 4), so the result of the block can't mention it):let xwithdef k iff P xas the last line would otherwise give∀ x (k iff P x), which makeskmeanP candP dat once. Adefat the top level is exported with its label as before; one in a block never is. After the block the name is unknown again, and a later block may define it anew (def t = 3in one proof,def t = 4` in the next).

    inline: a definition applied while reading. A def is a fact, and using it is a step: from x > 0 to 0 < x takes a line, and inside a formula a rewrite. When two notations should simply be the same, inline defines the new symbol by what it is read as:

    inline $a > $b   iff  $b < $a          ; number.kurt (also `>=`)
inline $a ≠ $b   iff  not ($a = $b)    ; equality.kurt
inline $A ⊃ $B   iff  $B ⊂ $A          ; set.kurt (also `∉`)
inline sq $x     =    $x * $x          ; a term

    Each use of the symbol is read as the right side, with the arguments for the variables, so it is in no stored term: x > 0 is 0 < x, a rule written with < applies to a line written with >, and nothing is to be switched. Kurt prints the stored term (0 < x). The checks are those of def: the left side is a new symbol (used nowhere yet; its syntax, infix >, may be declared before), alone or applied to distinct variables; the right side has only these variables, not the symbol itself, and no binder (an argument could be captured by it -- use def there). = for a term, iff for a formula. A parameter may also be a tuple of variables, inline child($x, $y) iff parent($y, $x) (an argument must then be a tuple of that length). inline without arguments lists the inline definitions; they are exported with load.

    Why not every def is an inline. inline is for notation: the same thing written differently -- a converse relation (>, ⊃, child), a negation (≠, ∉), a short abbreviation of a term. A def gives a concept a name that one reasons with: subspace(U), even n, group(G, ·), orthogonal(x, y). Inlined, such a name would disappear from every line and from Kurt's output (which prints the stored term), the formulas would grow, the search would get slower (more places where rules fit), and the step "by definition", which a reader of a proof wants to see, would be gone. Most definitions also contain a binder (even n ⇔ ∃ k ...), which inline refuses. So: def for what has a name of its own in mathematics and theorems about it, inline for another way to write the same thing (keywords/46-inline.kurt).

    6.3 todo¶

    todo          ; admit the next step (a claim, or the goal at `qed`)
todo EXPR      ; admit EXPR specifically, and add it to the theory

    A joker: lets a proof continue (and the file still finish, with Proof almost checked: N todos. instead of Proof checked, listing every todo's file and line) even though a step hasn't actually been justified. Meant for iteratively developing a proof, or handing out a skeleton with gaps left as exercises. A later step that uses an admitted line cites it as 6 (todo) -- also with --all-errors, where a line that fails is admitted so that the check can go on.

    6.3.1 Definitions, axioms, admitted statements, and derived theorems¶

    The way a formula enters the theory determines its status. Its label does not:

    Source form Status What Kurt checks
    def name = term or def predicate(...) iff formula conservative definitional extension The syntactic conservativity conditions in §6.2. This extends the vocabulary without adding an assumption in the old vocabulary.
    use EXPR "label" axiom EXPR is well formed and a statement. Its mathematical truth and consistency are assumed. This includes recursive or other defining axioms.
    todo EXPR or a step admitted by todo admitted/incomplete Enough syntax and bookkeeping to continue checking. The file remains visibly unfinished.
    show EXPR "label" followed by proof ... qed derived theorem Every proof step and the final goal. show merely announces the planned claim; the theorem enters the theory when qed succeeds.
    EXPR "label" as an ordinary line derived theorem Kurt derives the line from facts already available, and its certificate is checked by the kernel.

    For example, all four labels below are only names; they do not override the admission form:

    def square($x) = $x * $x              "square-def"       ; definition
use fact(0) = 1                        "factorial-def"    ; axiom
todo P                                 "future-theorem"   ; admitted/incomplete
P implies P                            "identity"         ; derived theorem, if the line checks

    In particular, use ... "something-def" remains an axiom, and a proved theorem does not become an axiom because its label says axiom. A label controls how a fact is referenced and, together with the absence of local, whether it is exported by load (§8.2). It does not change the fact's provenance. This distinction is important when auditing a theory: a checked proof establishes its conclusion relative to the use axioms, defining axioms, calculator semantics, and any todos on which it depends.

    6.4 theory¶

    theory              ; print every formula, at every open level
theory OP            ; print only formulas whose top-level operator is OP

    Read-only introspection; changes nothing.

    6.5 cert¶

    cert 17             ; the certificates of line 17 of this file (or of the shell)
cert 17, 18
cert 12-15          ; the result of the block of lines 12 to 15 (`; 12-15 by impl-intro`)
cert                ; those of the last line with a step

    The comment after a checked line, e.g. by forall-cond-elim(8, 9), is a short form of the line's certificate: what the kernel checks again, on its own, for each step (see doc/kurt-soundness.md §9). cert shows it in long form: the rule and how it is read (as a fact, or as premise ⇒ conclusion), the values of its variables, the fresh variables for ∀s, the facts that match the premise -- or, for closing a block, the block and its last line. The kernel checks every step; should it ever reject one that the search found (a bug in Kurt), that is a KernelError, which stops the file and can't be caught by expect. Variables are shown with the names they were written with ($a, %A, x), numbered where several of them have the same name ($x1, $x2). A line that failed has no certificate; a line that closes blocks by dedenting also has the certificates of the closings.
