    8. Building the theory: hard-coded core vs. loaded theories¶

    8.1 What's hard-coded (needs no load)¶

    A pristine session starts with minimal.kurt's worth of syntax (space, comma -- a, b, c is one list, and (a, b, c) in round brackets a triple (§4.3) --, ( ), implies, and, the constant true, the substitution operator sub — sub $x $a %A is "%A with $a substituted for $x", only allowed in use/def to write axiom schemas like "forall-elim" or "equal-elim", and not nested (a rule about two variables is applied twice, one variable at a time); where the search finds $a and %A for a given formula, the hole $x is a subexpression -- a statement or a term --, and an operator only if it yields a term: see "Where the hole of sub may be" below) already declared -- the quantifiers forall/exists come with load logic (see below) -- plus these rules implemented directly in Python (not as use axioms you could remove):

    • "top-intro" — the bare symbol true is always provable.
    • "impl-elim" (modus ponens) — given A and A implies B anywhere in the theory, B is derivable.
    • "and-intro" — given A and B separately provable, A and B is derivable (and, symmetrically, a claimed conjunction is split into its conjuncts and each is derived separately).
    • "not-intro", automatically, as a side effect of closing an assume block (see §9.1) whose last derived line is literally false — this one isn't reachable as a standalone rule outside of that block-closing moment.
    • an iff as an implication — a fact A iff B (e.g. from def P iff ...) is used directly as A implies B and as B implies A, without a rule -- for the symbol with the role equivalence (propositional.kurt's iff, see builtin, §10).
    • "case-elim" — closing the case blocks of a disjunction (§9.1) gives the goal; it is justified by propositional.kurt's "or-elim", for any number of alternatives.
    • "chain-trans-I-J" — the transitivity rules a chain declaration generates (§4.6).
    • "by calc" — with calc on, a claim that computes to true, or to a fact, follows by the built-in calculator (§10).
    • forall-elim, effectively for free (with load logic) — every formula ever added to the theory has any outer universal quantifier stripped and its bound variable replaced by a fresh, freely-unifiable internal variable (as if it had been written as a $-schema to begin with) — so use forall x (A x) already lets A a derive for a specific a, with no explicit forall-elim step needed. The same for "forall-intro" (closing a let block) and "exists-elim" (closing a pick block). logic.kurt's forall-elim axiom still exists for the same reason a hard-coded rule sometimes also has a use equivalent lying around: explicit intermediate steps, and cases this automatic stripping doesn't reach (a forall that isn't the outermost operator of a stored formula). Only a forall without a condition is stripped: ∀ $x > 0 P($x) stays as it is, and is used via logic.kurt's rules for conditions (§4.4).

    Where the hole of sub may be. A rule like "equal-elim", ($a = $b) ∧ (sub $x $a %A) ⇒ (sub $x $b %A), rewrites a formula by cutting a hole $x into it. The hole is a part of the formula that is a term or a statement -- and an operator counts only when it is a term on its own. A function symbol is: f with arity f 1 is an object, which an equation can name. So f = g rewrites f a:

    load equality
const f, g, a
arity f 1, g 1
prop R
arity R 1
use f = g
use R (f a)
R (g a)                     ; by equal-elim(6, 7) -- the hole is the operator `f`

    An operator with a statement as its result is not: =, ∧, or a predicate P with prop P and arity P 1 is, on its own, neither a term nor a statement -- it becomes a statement only applied to its arguments. So the hole is never the = of c = c (doc/kurt-soundness.md §8.40: cut there, "iff-subst" had turned R ((¬¬(=)) c c) into R (c = c)), and a bare such operator where a statement is required is a type error -- also an equivalence of two predicates:

    load propositional
prop P, Q
arity P 1, Q 1
use P ⇔ Q                   ; TypeError: arg number 1 of `iff` must be a statement, but `P` is
                            ; an operator without its arguments -- apply it to its 1 argument, e.g. `P a`

    State it for the arguments instead: use ∀ x (P x ⇔ Q x) (with load logic), and P a gives Q a. A binder (∀, ∃) is no hole either. An operator variable (var ∘ with infix ∘) is a different thing: it matches an operator by itself, through the unifier (∘ := +), not as a hole.

    The quantifiers are declared in logic.kurt, which gives them their roles (builtin forall universal, exists existential, §10): the engine strips, closes let with, and opens pick from, only the binders with these roles. So the core has no quantifiers: a file for propositional or modal logic doesn't need them, a deep embedding may use the words for something else, and without load logic, let (over terms) and pick say that they need it.

    Notably, "and-elim" (splitting a proven A and B back into A) is not hard-coded — you either state the specific instance yourself as a use axiom, or load propositional for a general one. A general "restatement" schema (%A implies %A) and a general "impl-intro" schema ((%A implies %B) implies (%A implies %B)) are also not hard-coded, despite once being drafted as if they were: a bare A implies A with nothing else known does not derive from nothing. Prove a specific instance instead (show/proof/assume/qed), or note that plain "restating" an already-proven fact is covered anyway by "impl-elim"'s own premise-less- implication case.

    minimal.kurt is the core itself: Kurt reads its declarations when it starts, before anything else, and freezes them (only the parse rule of local and the internal marker of bound variables are made in kurt.py). It is never loaded -- load minimal is an error ("is the core, which every file starts with"). It deliberately declares no aliases: propositional.kurt supplies ⊤, ⇒, ∧, ∨, and ¬, and logic.kurt supplies ∀ and ∃.

    8.2 load and the theory library¶

    load NAME               ; load "path/to/name.kurt"
load NAME1, NAME2, ...

    load searches, in order: the loading file's own directory (or the current directory, from the CLI/shell), then any -p/--path directory given on the command line, then Kurt's own packaged theories (src/kurt/theories/). The .kurt extension is added automatically if missing. The packaged theories can't be shadowed: load propositional always loads Kurt's own propositional.kurt, and a file propositional.kurt found earlier on the search path is an error (rename it) — def, and the checks built on the packaged theories, rely on their exact content. (A name with a directory, load ./propositional or load lib/propositional, is your own file, as written — not trusted, so under --strict it may not use anything.)

    The symbols declared by a trusted theory file — one that comes with Kurt, or one found via -p DIR — are frozen: no other file can declare them flat or sym, or put them into a chain in a way that derives something new about them. E.g. chain ≠ (which would make ≠ transitive) is rejected, while chain = lt for a file's own relation lt is fine: a frozen operator may be combined with the file's own operators if the frozen ones come first (the chain's conclusions use the later operator) and are already chained that way in their theory. A file that has already finished loading is not loaded again (tracked via get_load_level, per level, inherited from parent levels) — so load propositional twice in a row, or from two different files that both depend on it, is a harmless no-op (logged as already loaded, skipped) rather than a duplicate-axiom error. A file that is still in the middle of loading (a genuine cycle: a.kurt has load "b.kurt", and b.kurt has load "a.kurt") is tracked separately and raises a clean EvalError: circular \load`: ...instead of recursing forever. The end of a loaded file closes the blocks still open in it, as a dedent does ([§7](goal-directed-proof.md), [§9](blocks-and-natural-deduction.md)): anassume/let/pick/casegives its result, asandboxis discarded -- nothing half-open leaks into your file. Aproofwhose goal isn't reached by then, or ashowwithout a proof, fails the wholeload`.

    Each file is checked on its own. A loaded file is checked in a fresh context, one level deep, inside an implicit sandbox of its own (which break can't close and summary doesn't list; the main file is checked the same way): the hard-coded core (§8.1) and the files it loads itself -- nothing of the file that loads it, not its facts, declarations, or calc on. So a library can't use a fact without loading the file it comes from, and the order of two loads doesn't change what either of them proves. What the file exports (below) is then added to the loading file. A symbol that both know must mean the same there: its declarations may not contradict each other (one side may have more, e.g. numbers.kurt binds = of equality.kurt to the calculator), and if it is defined by a def, it must be the same def on both sides -- a def is only conservative for a new symbol, so const f / use f = 1 here and def f = 2 in the loaded file is an error. A fact that two loaded files both pass on (from a file both of them load) is added once.

    A symbol is declared by one file only. The declarations of a symbol -- infix, prefix, postfix, arity, brackets, bindop, flat, sym -- come from the one file that declares it; Kurt remembers which (it travels with the exports). If two different files declare the same symbol, they can't be loaded together, in either order, directly or through other files:

    EvalError: `+` is declared in `numbers.kurt` and in `field.kurt` -- a symbol
is declared by one file only, so these two can't be loaded together

    The reason: a theory's laws hold for everything written with its operators. numbers.kurt says $a * $b = $b * $a for every $a, $b; a theory of matrices that declares its own · or + must not get those laws. So:

    • numbers (ℕ, ℤ, ℚ, ℝ): load numbers (or natural, integer, rational, analysis, which load it);
    • linear algebra: a structure that declares its own operators, like field.kurt, vectorspace.kurt (and proofs/mafi1/matrices.kurt) -- not together with numbers.kurt;
    • group.kurt takes its operation as an argument (group(G, (∘), e, inv)), so it goes with either.

    A theory loads what it uses. A file gets the symbols of the files that its loaded files load, too: after load natural, ∀ (from logic.kurt) and + (from numbers.kurt) are there. But a theory that relies on this breaks when the file in between stops loading them. So a trusted theory -- one that comes with Kurt, or one from a -p directory -- gets a note for a symbol of a theory it doesn't load itself:

    ; note: `forall` comes from `logic.kurt`, which this file doesn't load itself --
; `load logic` makes it independent of what the other files load

    The theories that come with Kurt load everything they use (a test checks it). For a proof, this isn't noted -- load numbers and then = is fine -- but kurt --deps lists such symbols for any file (§1).

    The same file reached twice (two files both load numbers.kurt) is one declaration, not two. (numbers.kurt used to be called arith.kurt.) In one run of Kurt, a file is checked once and its exports are reused, as long as neither it nor a file it loads changed; only the file you check itself is always checked again (it prints its steps).

    The packaged theories (src/kurt/theories/), and roughly what each adds, declaring their own prerequisites via their own load lines:

    modal.kurt is the packaged modal theory. A modal formula is a Kurt term, not a statement, so its metavariable is $A; object connectives such as →, ∧, and □ only construct such terms. The judgment ⊢ $A, a statement, says that the term is an object-level theorem. Therefore necessitation is the ordinary Kurt schema (⊢ $A) implies (⊢ □$A), while object modus ponens has the two Kurt premises ⊢ $A and ⊢ ($A → $B). The turnstile is declared both prefix and infix: prefix ⊢ A means theoremhood, binary G ⊢ A means derivability from a represented context, and two explicit rules identify prefix theoremhood with empty ⊢ A. proofs/logic-encodings/ contains a small sequent calculus and an ordered-resource experiment without exchange, weakening, or contraction.

    modal.kurt declares the optional sort formula for the formulas of modal logic, so a modal formula can't be written as a claim by itself (use □P → P is an error) -- a claim is ⊢ A, "A is a theorem". The theory still owns → and □, so it cannot be loaded together with set.kurt (where → is a function-space constructor) without future namespaces.

    The former shallow theory with the same filename could not express sound necessitation because its formulas were Kurt statements: %A implies □%A also applied below an assumption. It was replaced. Moving the pretty aliases out of the minimal core lets the current modal.kurt own the paper symbols ∧, ∨, and ¬ as formula constructors without changing their role in propositional.kurt.

    lambda.kurt is another deep embedding. Its type, term, index, ctx, and typing sorts reject malformed typing judgments before proof search. De Bruijn terms at zero, at (succ zero), and abs A M give complete variable, weakening, abstraction, and application rules using explicit contexts. Those judgments have the conventional surface Γ ⊢ M : A; the older prefix form has Γ M A remains available for compatibility. The theory also provides readable named terms: λ is a real Kurt binder, so alpha-equivalent terms match, and its beta rule uses sub for capture-avoiding substitution. Compatible application rules give weak beta reduction ↦; ⇝ is a deterministic left-to-right call-by-value relation with explicit values. The executable examples include a concrete preservation instance and a finite confluence diamond. General preservation and Church–Rosser need induction over encoded derivations (and a substitution lemma or parallel reduction), which the current first-order theory does not supply automatically. Pure Kurt currently expresses several sound named typing conveniences rather than the full named hypothetical-context abstraction rule; the de Bruijn representation supplies the general rule without extending the language. See tutorial/27-type-and-reduce-lambda-terms.kurt.

    What gets exported¶

    Not everything a loaded file declares becomes visible to whoever loads it. A use/def axiom or a proved (show/proof/qed) theorem is exported exactly when it carries a label and that label isn't marked local (§6.2) — an unlabelled fact, or one labelled EXPR local "...", stays entirely inside the file that wrote it. A symbol is exported when an exported fact mentions it, or when the file declares it at its top level: a declaration written out there (const, prop, infix, prefix, postfix, brackets, arity, bindop, flat, sym, chain, alias, tex, lean, a sort's signature) is the file's vocabulary. Either way, all that is known about the symbol travels along (its arity and shape, fixity, statement places, tex, lean, ...), so it can still be parsed and type-checked downstream. Not exported are: a declaration with local at its end (const helper local, prop Q, R local -- for the whole line), a declaration inside a block, var (a loaded var x would make the loader's x a variable), and the constants Kurt adds by itself at a symbol's first use (; added constant). So a symbol that only ever appears in local facts and isn't declared at the top level (or only with local) is invisible from outside, freeing up its name for something else entirely unrelated in whatever file loads this one; a local declaration of a symbol that an exported fact needs still goes along with that fact. (Before 0.9, a declaration alone exported nothing.) A symbol bound to the calculator (builtin + add, §10) is exported too, even without a fact that mentions it: the binding is an axiom about it (1 + 1 = 2, ...) -- e.g. matrix.kurt's literals [ ], det, transpose. An alias (alias) travels automatically with whatever symbol it names, since an alias never itself appears written out in a formula — axioms are always written with the canonical name.

    This makes def's two halves — the new symbol, and the fact defining what it means — travel together when exported. If a def is marked local but some other, exported fact in the same file still needs that symbol, the file fails to load with a clear error naming the symbol, rather than silently promoting the local marking away or silently leaving the symbol meaningless downstream.

    The var declaration itself is file-local regardless of labelling. Before a formula is stored, however, each of its declared free variables is replaced in the formula's proof representation by a fresh internal schema variable. Its local inferred type does not occupy the printed name in the loading file. Therefore a labelled exported formula remains schematic: var p, q followed by use p and q "pq" can match A and B after load, even if the loading file uses the printed names p and q as constants. This also applies to variables in function, infix, prefix and postfix operator position. Parser-facing declarations such as arity f 1 and infix ∘ 70 70 still travel so the notation remains writable, but the variable role does not. The original expression is retained for source and normal display; generated internal names never become part of Kurt source. Normal output makes this conversion visible beside the original use as ; schema: ... (§6.2), using stable $/% names instead of the internal fresh names.

    Example:

    ; helper.kurt
load propositional
prop P
prop Q local                     ; the declaration stays inside helper.kurt
use P            "exported"      ; travels to whoever loads helper.kurt
use Q            local "hidden"  ; stays inside helper.kurt
def R iff P      "also exported" ; R travels too, since it's labelled

; main.kurt
load helper
P                 ; fine -- P was exported
R                 ; fine -- R (and its definition) was exported
Q                 ; ProofError: can not derive `Q` -- never exported, so as far as
                  ; main.kurt is concerned `Q` is just a fresh symbol with no axiom
                  ; behind it (§3.4), not literally an "unknown symbol" error

    save: keep a shell session as a file¶

    save "path/to/file.kurt"

    Writes the input lines that were accepted so far to path (relative to the current working directory): in the shell, the session without the lines that failed, and without the ones that only show something (theory, cert, help, a declaration without arguments, ...); in a file, its lines so far. The result is ordinary Kurt source, which proves its results again when it is checked, and gets its certificates in a .kurtc then (§1) -- nothing is taken over as an axiom. save needs all blocks closed and no pending show, since otherwise the saved file wouldn't load. load lines are kept as typed, so a saved file finds its theories as the session did (e.g. relative to the working directory). The name must end with .kurt and not be the name of a theory that comes with Kurt, and save works neither with --strict nor in a loaded file -- it writes the checked file's (or the shell's) own lines, nothing else.
