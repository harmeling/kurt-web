    1. Running Kurt¶

    kurt                        # start the interactive shell (a REPL)
kurt path/to/proof.kurt     # check a proof file, then exit
kurt -i path/to/proof.kurt  # check the file, then drop into the shell (after an error: at the failing line)
kurt -d path/to/proof.kurt  # also print debug information
kurt -v                     # show the version (also `-V`, `--version`)
kurt -p DIR path/to/proof.kurt   # also search DIR for `load`ed theories
kurt -s path/to/proof.kurt       # strict, for grading (see below)
kurt -a path/to/proof.kurt       # all errors, not only the first (also `--all-errors`, see below)
kurt --budget 10 path/to/proof.kurt  # at most 10 s of search per line (see below; by default no limit)
kurt --profile path/to/proof.kurt    # after the check: the slowest lines, with their time and search steps
kurt -r N path/to/proof.kurt     # set the comment/reason column to N (default 42)
kurt --no-kurtc path/to/proof.kurt   # neither write nor use `.kurtc` files (see below)
kurt path/to/proof.kurtc             # the certificates of proof.kurt, readable (see below)
kurt --deps path/to/proof.kurt       # the files it loads, and their certificates (see below)
kurt --json path/to/proof.kurt       # the result as JSON, for graders and editors (see below)
kurt --unused path/to/proof.kurt     # check, then name the lines of the proofs that nothing cites (see below)
kurt --foundation path/to/proof.kurt # check, then show what each of its facts rests on: axioms, definitions, todos (see below)
kurt --foundation gauss proof.kurt   # ... only for the fact "gauss" (or at a line: --foundation 12)
kurt --latex path/to/proof.kurt      # the checked file as a document, proof.tex (also --markdown: proof.md; see below)
kurt --lean path/to/proof.kurt       # ... as a Lean 4 file, proof.lean (a prototype; see below)
kurt --lean proof.kurt -o -          # -o FILE: to FILE instead, -o -: to the standard output
kurt --no-line-numbers proof.kurt    # the output without the source line numbers in front
kurt --share path/to/proof.kurt      # the playground link of the proof (its text in the link; see below)
kurt --unshare LINK > proof.kurt     # the proof of such a link, back (see below)
kurt --lsp                           # a language server for editors (see below)

    In the browser: the playground, www.kurt-lang.org, runs the same Kurt, checked as you type, with the tutorial, the keyword lessons, the exercises, the theories and the proofs of a lecture in its menus. A link can open one of these files: https://www.kurt-lang.org/#file= followed by its path in the playground, e.g. #file=exercises/01-knights-and-knaves/2-two-islanders.kurt, #file=tutorial/02-prove-an-implication.kurt or #file=theories/set.kurt; it shows the file's current version, and an exercise loads its scene. "Copy link to this proof" (in the menu File) gives such a link for a file opened from a menu, as long as it is unchanged; for an edited one, the link contains the text itself.

    If no filename is given, Kurt starts the shell directly. If a filename is given without -i, Kurt checks the whole file, prints Proof checked (or, if any todos are left, Proof almost checked: N todos. plus a list of where they are) and exits with code 1 if checking the file raised an error (0 otherwise) — so a script (CI, an autograder) can tell a failed check from a successful one without scraping stderr text. Leftover todos still exit 0 (a todo is a deliberate, self-reported placeholder, not a failure), and errors raised only while typing at an interactive shell session don't affect the exit code either.

    All errors (-a/--all-errors): by default, a check stops at the first error. With -a, it goes on after an error in the checked file, so it finds all errors that don't depend on each other; each is printed when it is found, the lines after it get their reasons as usual, and the file ends with Proof not checked: N errors. (exit code 1). To go on, Kurt does internally what a student would do to get past the error -- the file isn't changed:

    • a formula that can't be derived is admitted, as todo would (so the lines that use it don't fail because of it);
    • a block that doesn't close -- a proof whose goal isn't reached, also at the end of the file -- is closed anyway, and its claim counts as admitted (any other block is discarded, as break does); the line that closed it is then checked on its own;
    • a claim without a proof counts as admitted;
    • any other line (one that can't be read, a wrong use of a keyword, a type error) is dropped, as in the shell; if it opens a block, the block is skipped too, and so is the proof of a show that can't be read. A dropped line may cause later errors (e.g. a def that failed).

    The admitted lines are errors, not todos: they aren't listed as todos, the file gets no .kurtc, and the result is failed. Some errors still stop the check: an error in a file it loads (and on a load line), anything inside an expect block (there the error is the expected result; §9.6), and a KernelError. The editors (kurt --lsp) and the playground show all errors by default; from Python, kurt.RunConfig(all_errors=True), and CheckResult.errors lists them (error is the first one).

    Where a proof is slow (--profile): kurt --profile proof.kurt checks the file as usual and then prints, on stderr, its ten slowest lines with the time and the search steps of each (the load line has the time of the files it loads, cached files cost nothing):

    the slowest lines of proof.kurt (1.37 s in all, seconds and search steps):
    0.85 s        0 steps      1  load logic, number
    0.40 s     1200 steps     14  x + y = y + x

    From Python, kurt.RunConfig(profile=True) fills CheckResult.profile (also in --json): a record file, line, seconds, steps for each line. The editors (kurt --lsp) mark a line that took 2 s or more with an Information diagnostic (slow line: 2.4 s, 5300 search steps) and write the time into the hint at its end. An editor that asks for it (the initialization option heat: VS Code's kurt.heat.enabled) also gets two notifications: kurt/progress (the line being checked, at most ten times a second, for tinting the lines done and the line at work) and kurt/profile (time and steps of each line, after the check, for a heat map of the lines). kurt/cancel (with uri) from the editor stops the check that runs, at its next step (the editor is told by kurt/progress with done and cancelled); VS Code's status item shows Kurt: checking 12/84 and a menu with the cancel.

    Budgets (--budget SECONDS), and cancelling a check: the search for one line normally takes a fraction of a second, but a false claim among many facts can take minutes (the search tries every combination before it gives up). A budget stops it: kurt --budget 10 proof.kurt allows each line 10 s of search; a line that takes longer fails with a ResourceError:

    ResourceError: the search for this line stopped after 10 s, its budget -- the line is
neither proved nor refuted; a larger budget may decide it (...)

    It is a kind of its own, apart from a ProofError (a rejection): the budget says nothing about the line, only that the search didn't finish. A budget never changes which steps are accepted -- it only stops the search early -- and the kernel isn't involved. With --all-errors, the check goes on after it as after a ProofError (the line is admitted, see above); expect can't name ResourceError (as it can't name KernelError), so a proof file can't depend on a budget, and an expect "ProofError" whose line runs out of budget is an error, not confirmed. The command line has no budget unless --budget says so; the editors (kurt --lsp) allow 30 s per line (the initialization option budget, 0 for none), the playground the same, and scripts/grade_exercise.py too (--budget SECONDS). The budget applies to every line checked, also in the files a proof loads.

    From Python: kurt.RunConfig(time_limit=10) (seconds), kurt.RunConfig(step_limit=5000) (steps of the search: a goal against one fact, or a premise against the facts -- about 1000 to 4000 a second, the same on every machine), or both; CheckResult.exhausted says that a line's budget was used up (its errors entry has the kind ResourceError), and so does the JSON of --json. kurt.RunConfig(cancel=f) asks f() at every step and every line, and stops the check with a ResourceError at the current line when it returns true (CheckResult.cancelled; the lines after it are not checked, also with all_errors) -- e.g. cancel=event.is_set for a threading.Event another thread sets. The language server uses it to stop the check of a text that was edited meanwhile (before, the check of the new text waited for it), and the client's $/cancelRequest; an embedder of the server sets LanguageServer.cancel = f to stop its check the same way (the playground: f reads a flag in a SharedArrayBuffer that its Cancel button sets, so its worker, busy with the check, needn't be killed).

    Progress, from Python: kurt.RunConfig(progress=f) calls f with a dict when a file starts, at each of its statements and when it is done: file, line (of lines), index of files (the files checked so far -- a theory that the session has checked before and that didn't change is not checked again) and done. The playground shows it as a progress bar.

    Strict mode (-s/--strict), for grading: the checked file (and any file it loads that isn't trusted) may not contain use or todo, a chain there needs its rules proved before it (§4.6), and every symbol must be declared before its use (§3.2), and calc may not bind symbols to the calculator — everything has to be proven from the theories that come with Kurt, or from the ones found in a -p DIR directory (e.g. an exercise's axioms, as given by the teacher). Those are the trusted theory files; use inside a sandbox or expect stays allowed, since their content is discarded. It is a command-line switch rather than a statement in the file, so that the file being graded can't switch it off.

    Certificates of a file (.kurtc): after a file checks completely (no error, no todo), Kurt writes foo.kurtc next to foo.kurt (if the directory is writable) -- the certificates of its claims (§6.5), in JSON, with the hash of the file and the files it loads. When foo.kurt is checked or loaded again, unchanged, each claim first tries its stored certificate: rebuilt with the facts as they are now (a step of the line itself that it cites, 17a, from its own stored certificate first), and checked by the kernel; only if that doesn't work, Kurt searches as usual. So the output is the same, it is just faster (for the proof files of this repository, up to five times). A .kurtc can't make Kurt accept anything the kernel doesn't check -- a wrong or outdated one only costs the time of the search -- so it is also used with --strict. Kurt writes and uses .kurtc files when run as kurt (the command line or shell); from Python, only in a session with kurt.RunConfig(kurtc=True) -- for a text (check_text), only for the files it loads, not for the text itself. kurt --strict foo.kurtc checks foo.kurt with the same options as kurt --strict foo.kurt.

    The theories that come with Kurt come with their certificates: the package has them next to the theories, and the single-file kurt.py embeds them (scripts/build_certificates.py makes them). In them, a theory of Kurt is named <kurt>/propositional.kurt, not by where it is, so they fit wherever Kurt is installed. If a theory's directory isn't writable, its new certificates go to the cache directory ($XDG_CACHE_HOME/kurt, or ~/.cache/kurt). A .kurtc that is up to date isn't written again. (Without them, load divisibility in the single-file kurt.py took 8 s each time, 1.2 s with them.)

    kurt --json foo.kurt checks the file and prints the result as JSON (exit code as above): ok, complete (also no todo left), error, error_kind, error_line, failure (why a step failed, §6.1), errors (each with its kind, line, column, message, failure, and the file for an error in a file it loads; with --all-errors all of them, else the one), exhausted and cancelled (a budget was used up, the check was cancelled; see above), todos, loaded (the files it loaded, also through other files), certificates (of each line, as cert shows them), the text output, and events, each printed line as a record -- the source line, its id (5, 5a, 11-13), its kind (step, claim, open, close, assumed, load, declaration, expect, error, text, other), level, text, the rule and the lines it uses, its label, the user's comment, and where they apply its steps and schema:

    {"line": 5, "id": "5", "kind": "step", "level": 0, "text": "B", "reason": "5 by rule(4)",
 "comment": "modus ponens", "rule": "rule", "uses": ["4"]}

    From Python, the same comes from kurt.check_file(path) or kurt.check_text(text) (a CheckResult, with .events and .to_json()). A text is never trusted (under strict, it may not use), whatever name it is given -- trust comes from where a file is read. One exception, for the editors: a text under the path of a theory of the running Kurt that is exactly that file's text (saved, unchanged) is that theory, trusted like it; a changed text is not. Like the command line, the module refuses to check under python -O (which removes Kurt's internal checks).

    Does the file prove a given theorem? ok and complete say that the file checks (an empty file is complete), not what it proves. result.proves(statement, label=None) says whether the file proves statement at its top level: derived in this file by steps that rest on no admission -- not a use or def, not a todo or a claim whose proof contains one (anywhere in the proof, needed or not) or uses a fact that was admitted (a todo F before it, a claim admitted after an error with --all-errors), not a fact of a loaded file, not a claim that is withdrawn (break) or only proved inside a block. With label (or a label written in the statement, proves('A ⇒ B "ab"')), the fact must carry that label; without one, any label will do. The statement is written as Kurt reads it, with or without show, and is read in the file's final context: A ⇒ B and A implies B are the same statement, A ∧ B and B ∧ A too (∧ is sym), and a statement the file can't read (a notation it doesn't declare) is one it doesn't prove. result.proof_of(statement, label=None) says how the file states it: 'proved', 'admitted' (a todo, or a proof that rests on one or on an error), 'assumed' (use, def), 'loaded' (a fact of a file it loads, not proved here), or None (not stated at the top level); when it is stated more than once, the best counts. result.loaded lists the files the check loaded, directly or through other files, by their paths -- a grader checks it against the files a solution may load (scripts/grade_exercise.py: only what the exercise loads; a file that states the answer is no proof, even if the solution derives the answer from it in one step). Neither says anything after a check that stopped at an error (proves is false, loaded empty); with all_errors, the check runs to the end, and proves tells the claims whose proofs are sound from the ones admitted after an error.

    >>> result = kurt.check_text('load propositional\nprop A, B\nshow A ∧ B ⇒ A "a"\nproof\n    assume A ∧ B\n        A\nqed\n')
>>> result.proves('(A and B) implies A'), result.proves('A ∧ B ⇒ A', 'b'), result.proof_of('A')
(True, False, None)

    A proof as a link (--share, --unshare). The playground's Share button makes a link that holds the whole proof: https://www.kurt-lang.org/#proof=CODE, where CODE is the text of the file as UTF-8 bytes in base64 with - and _ instead of + and /, without the = padding (no compression, nothing secret: anyone can read it; an optional &folder=tutorial/ after it says where the proof's loads find their files). kurt --share foo.kurt prints that link for a file (it doesn't check it), and kurt --unshare LINK prints the proof of a link, or of the bare CODE, so that kurt --unshare LINK > foo.kurt gives a file to check. A very long proof makes a link that browsers and chat programs may cut (a few thousand characters): for a file that the playground has, #file=exercises/01-knights-and-knaves/2-two-islanders.kurt is short. The same without Kurt, in Python:

    import base64
def share(text):                  # the link of a proof
    return 'https://www.kurt-lang.org/#proof=' + base64.urlsafe_b64encode(text.encode('utf-8')).decode().rstrip('=')
def unshare(link):                # the proof of a link
    code = link.split('#proof=')[-1].split('&')[0]
    return base64.urlsafe_b64decode(code + '=' * (-len(code) % 4)).decode('utf-8')

    or in a shell, python3 -c "import sys,base64; print('https://www.kurt-lang.org/#proof=' + base64.urlsafe_b64encode(open(sys.argv[1],'rb').read()).decode().rstrip('='))" foo.kurt. (In the library: kurt.kurt.share_link(text) and unshare_text(link), which also gives the folder.)

    What a fact rests on (--foundation). kurt --foundation foo.kurt checks the file and then shows, for each fact at its top level, its class -- axiom (use), definition (def), todo, or theorem (a proved line, or a show with its proof) -- and, for a theorem, what it rests on: the use axioms and defs that the steps of its proof cite, directly or through the facts they cite, by file; the todos that admit a step; the steps computed by the calculator (calc on), with the symbols' bindings and the file whose builtin made them (`+` add, `=` eq of number.kurt). A fact without a label is named by its line (line 12), with its statement in its own heading: an unlabelled use is an axiom of the file like a labelled one (only it isn't exported). Found by walking the certificates of the steps (§6.5): through the blocks (a block's result rests on what its last line rests on; the block's own assumption is discharged when it closes, so it is no postulate), and into the theories it loads (a loaded theorem brings what it rests on in its file). A theorem with no todo behind it is established, relative to these axioms and definitions; one with a todo (or, with --all-errors, a line admitted after an error) is accepted relative to it. The class of a fact stays what it is (§6.3.1): use is an axiom, also where it could be proved. After the facts, the reverse: each postulate with the facts that rest on it -- for a change of an axiom, this is who is affected. For a teacher choosing a trusted set of theories: which uses a theorem really needs. kurt --foundation LABEL foo.kurt (or kurt foo.kurt --foundation LABEL) shows one fact, found by its label or its line: a theorem with what it rests on, an axiom, definition or todo with the facts of the file resting on it. In an editor (kurt --lsp), the hover of a theorem at the top level says it in one line: "rests on: 2 axioms of gauss.kurt, 3 axioms of natural.kurt, 1 def, the calculator, no todo".

each postulate, and the facts above that rest on it:

    The rules a chain declaration stands for appear as the rules of `chain = < <=`. From Python, check_file(path, foundation=True) (and check_text) fills CheckResult.foundations, one record per fact -- label, line, file, text, class, status (established/accepted, or the class of an axiom, definition or todo) and rests_on, each postulate with its kind (use, def, todo, calc, admitted), file, line, label and text (and for calc, bound_in: the files of its bindings) -- and result.foundation("gauss") finds one by its label (or line); kurt --json includes them as foundations. Nothing is stored for this: it is computed from the certificates after the check, so it costs nothing where it isn't asked for.

    kurt --lsp is a language server (the Language Server Protocol, over stdin/stdout) for editors -- VS Code (the extension of kurt-syntax), Emacs (Eglot), and Neovim. A file is checked when it is opened and saved. A client can request debounced checks while typing. Errors and todos appear as diagnostics at their lines, the reason of each checked line appears at its end (an inlay hint) and on hover; what a line prints besides a reason (builtin, infix, theory without arguments, cert 14, ...) appears on hover too (its first 60 lines); a line without a certificate says on hover what it does, with its own symbols (var a, b: "a, b stand for anything ..."; infix ^ 75 74: right-associative; calc on, tex, ...); a theorem at the top level says what it rests on ("rests on: 3 axioms of propositional.kurt, 1 def, no todo", see --foundation). A line inside a proof that nothing cites is greyed out (a hint with the LSP tag "unnecessary", as an unused import), and kurt --unused names these lines: backwards from what must stay -- the top-level lines, the labelled ones, qed, and a proof's last line that is its goal -- along what each step cites; a block's result cites the block's last line and its first, so a block whose result nothing needs is greyed out entirely. A line that restates a block's result (∀ x Q(x) after a let block), an assumption, or the line before it isn't greyed out: it helps the reader, and the hover says that Kurt doesn't need it. Only lines of proof, assume, let, pick and case blocks are reported, and only of a file without errors; "nothing cites it" isn't "it could be deleted" (a step may be found without citing a line that helped). And completion knows the state at the cursor (the next step, the value after = with calc on, LaTeX shortcuts, theories, and names). Positions use the LSP's UTF-16 convention, so mathematical symbols before a completion or hint do not shift it.

    The initialization options are theoryPaths (additional trusted theory directories), strict, allErrors (all errors of a file, the default; false: only the first, as kurt without -a), budget (seconds of search per line, 30 by default; 0 for none; a line that takes longer gets a ResourceError diagnostic, see "Budgets" above), checkOnChange (also accepted as checkOnType), and checkOnChangeDelay in seconds. A check of a text that is edited while it runs stops at its next step. The directory of the edited file is searched first but remains untrusted; only an explicit theory path grants trust. When an open document loads another open document, Kurt checks the current unsaved text of the loaded document. Closing a document clears its diagnostics.

    kurt --deps foo.kurt shows the tree of the files that foo.kurt loads (read from their load lines, before anything is checked), each with the state of its certificates and the dates of the file and its .kurtc:

    gauss.kurt  -- certified  (file 2026-09-29 06:11, certificates 2026-09-29 06:13)
└─ analysis.kurt  -- certified  (file 2026-09-28 16:11, certificates 2026-09-29 06:13)
   └─ natural.kurt  -- out of date: the file changed since  (file 2026-09-29 07:02)
      ├─ set.kurt  -- certified, but logic.kurt changed since  (...)
      ...

    "certified, but ... changed since" means: the certificates fit the file, but a file it loads has changed -- they are still tried (and checked by the kernel) the next time, and rewritten after it.

    After the tree, --deps checks foo.kurt (quietly) and lists the symbols it uses from theories that it doesn't load itself, by theory -- e.g. logic.kurt: `forall` for a file that loads only natural and writes ∀ (see load, §8.2).

    The .kurt file is the only source of truth. Everything else is derived from it, can be deleted, and is never trusted: a .kurtc only holds hints, which the kernel checks each time; the reasons Kurt prints and cert only show a check that already happened; and save writes Kurt source again, not a snapshot of facts.

    kurt foo.kurtc shows the certificates of foo.kurt, line by line, as cert does: the goal, the rule (with its file and line), the values of its variables, and the facts it uses, and the blocks it closes. Kurt checks foo.kurt for that (quietly, with the .kurtc), so what is shown was checked by the kernel; the first line says whether the .kurtc still belongs to the file.

    Documents and Lean (--latex, --markdown, --lean, -o). A checked proof as a document: kurt --latex proof.kurt writes proof.tex, kurt --markdown proof.kurt writes proof.md -- each line in mathematical notation, indented by its block, with its reason, and then the certificates. A line that continues a chain is written as in mathematics, its relation and its right side (= x), without the left side Kurt repeats. How a symbol is written comes from its theory:

    tex alpha \alpha                    ; a symbol
tex sum \sum_{$1=$2}^{$3} $4        ; $1, $2, ... the places of the arguments, in the order of
                                    ; the shape (`arity sum _ (_, _) _`: the variable, a, b, T)

    (only output: nothing Kurt checks changes; exported with load). The tex lines, and the lean lines (below), belong in the theory files, with the symbols they write -- not in a file of their own (decided 2026-10-23); Kurt's theories in src/kurt/theories/ keep theirs there. Without a declaration, Greek letters and symbols are written by their LaTeX names, longer names upright (\mathrm{abs}), and a variable $x as x -- as \mathsf{x} only where a constant x is in the same formula.

    A Lean 4 file of a checked proof (a prototype): kurt --lean proof.kurt writes proof.lean (it doesn't run Lean; the last line Kurt prints is the command for that), and lean proof.lean checks it again with Lean's kernel. It writes each step from its certificate -- the rule with the certificate's values, and its premise from the cited facts -- and the theories' rules as Lean axioms (but those with a proof in Lean, see below), so Lean checks the proof, not the theories. Kurt's objects are one type Obj, its statements Prop; a flat or sym operator comes with its associativity or commutativity as an axiom (that is what the declaration asserts), ∀ x ∈ A P is ∀ x, x ∈ A → P and ∃ x ∈ A P is ∃ x, x ∈ A ∧ P (§4.4's "forall-cond-def"/"exists-cond-def"), any other binder is a constant applied to fun x => ... (sum i (a, b) T is sum a b (fun i => T); logic.kurt's ∃! x P(x) is what its definition says, ∃ x, P x ∧ ∀ y, P y → y = x, by its lean), a def is a Lean def with its defining equation proved by rfl (a def inside a block an obtain ⟨t, h⟩ : ∃ t, t = R := ⟨R, rfl⟩ in the proof, local as in Kurt; a def over a tuple, def coprime($a, $b) ⇔ ..., a function of the components, coprime a b; the defs of the symbols in what a step cites of a loaded file are Lean defs too), a case step rcases, and a symbol that is applied and also an object (f a, f ∈ (A → B)) is an Obj applied with k_apply. Without a number theory, a number is a constant of its own (k_num_17 : Obj; 0 and 1 of field.kurt are its zero and one, which only its axioms describe -- Kurt knows nothing else of them there), and a calc step is not translated: a sorry, listed at the end of the file. The rules of propositional.kurt, logic.kurt and equality.kurt are theorems of Lean's logic (each lean "label" grind, see below; invimplies by its lean), so Lean checks the logical rules a proof uses, with or without Mathlib.

    With Mathlib (numbers). A theory says how its symbols read in Lean (with Mathlib, but for propositional.kurt's lean invimplies ($2 → $1) and logic.kurt's ∃!), as tex does for LaTeX (raw to the end of the line, $1, $2, ... the places of the arguments; one template per number of arguments, so - has two; only output, exported with load):

    lean Obj ZFSet                      ; the Lean type of Kurt's objects (set.kurt)
lean real ℝ                          ; the Lean type of the sort `real` (number.kurt), embedded into it
lean complex ^ k_cpow $1 $2          ; the `complex` profile of the overloaded `^` (complex.kurt)
lean + $1 + $2
lean - $1 - $2                      ; `a - b`
lean - -$1                          ; `- a`
lean - opaque $1                    ; `- a` has no Lean meaning here: a constant of its own
lean ! Real.Gamma ($1 + 1)
lean Nat member $1 ∈ Set.range (fun n : ℕ => (n : ℝ))     ; what `x ∈ Nat` means
lean {_,...,_} k_numset (fun x_ => ∃ k_ : ℕ, x_ = $1 + k_ ∧ x_ ≤ $2)   ; a set with `...`, by its shape
lean lim (Filter.limUnder (nhdsWithin $1 {$1}ᶜ) $2)        ; a binder: `lim v a T`

    A lean declaration replaces the one of a file it loads (for the same number of arguments). An overloaded operator (§5.2) is written by the least sort of each occurrence: lean SORT OP TEMPLATE for the profile of that sort, else the operator's own lean (+ of ℝ or of ℂ: Lean's + either way), its arguments cast to the profile's type. A binder's places are its condition (if it has one) and its body, both as functions (fun x => ...), and the arguments between them, a range (a, b) as two (sum i (a, b) T: $1 a, $2 b, $3 the body). member declares a set of numbers: a definition, the set of the embedded numbers with the property (k_numset), and what membership in it means a theorem (k_mem_Nat : ∀ x : ℝ, k_emb x ∈ Nat ↔ x ∈ Set.range ...) -- from it the rules about the set are theorems. A set written with ... has the lean of its shape, {_,...,_} for {a, ..., c}, {_,_,...} for {a, b, ...} (the places are its elements).

    A model of a theory's own operations. lean SYMBOL def TEMPLATE makes the template a Lean definition (@[irreducible] noncomputable def, named by the symbol and the number of arguments), and the terms use its name -- they stay small, and the laws of a flat/sym operator are proved by unfolding it. A numeral can be mapped like a symbol (lean 0 ...) where no theory of numbers gives it a type. field.kurt is the example: K is the set of the embedded reals, and the operations decode their arguments (k_dec, the inverse of k_emb), compute in ℝ and embed the result:

    lean K def ZFSet.range (fun x : ℝ => k_emb x)
lean 0 k_emb (0 : ℝ)
lean + def k_emb ((k_dec $1 : ℝ) + (k_dec $2 : ℝ))

    modal.kurt has a model of its own as the objects (lean Obj ((Nat → Nat → Prop) → Nat → Prop), Kripke semantics): kurt --lean field.kurt and kurt --lean modal.kurt prove every axiom of the theory true in its model (doc/kurt-soundness.md §11).

    Sets and numbers. Kurt's objects are the sets of Mathlib's model of ZFC (ZFSet, set.kurt's lean Obj ZFSet), and a sort with a type of its own -- number.kurt's lean real ℝ -- is embedded into them, as real ⊂ set says: k_emb : ℝ → Obj is a definition (an ordinal for each real, by a well-ordering, and its von Neumann level), injective by Mathlib's theorems, so nothing is assumed. A variable, constant or binder of the sort real is a real (∀ x ∈ Nat over ℝ, x a number by its places or default real), every other object a set; a number at the place of a set is k_emb x (1 ∈ A is k_emb 1 ∈ A, {1, 2} Lean's own {k_emb 1, k_emb 2}, (1, c) the Kuratowski pair ZFSet.pair), and = between a number and a set compares them as sets. In set.kurt ∈ is ZFSet's membership, ∅, ∪, Pow, ×, A → B (ZFSet.funs) Mathlib's, {z ∈ A | P} separation (ZFSet.sep; a part chosen among the numbers, {n ∈ Nat | n > 2}, with the property read on the embedded numbers, k_lift), a mapping applied, f a, the b with (a, b) ∈ f (k_apply, a choice), and every rule of set.kurt, its theorems and the rules of a set by its elements ($x ∈ {a, b, c} ≡ ...) are theorems of Mathlib. So a proof that mixes sets and numbers is checked against one model of both -- no axiom of set.kurt is read over the reals. The rules of propositional.kurt, logic.kurt and equality.kurt are proved once for every type (∀ {α : Type u}: their variables without a sort), so "forall-elim" applies to ∀ x ∈ Nat over the reals and to ∀ x over the sets alike. Without set.kurt and the numbers (field.kurt, group.kurt, vectorspace.kurt: no sorts), the objects stay an opaque Obj.

    The theories of numbers all read Kurt's numbers as Mathlib's reals ℝ (number.kurt's lean real ℝ; Real, Int, Rat of number.kurt and natural.kurt's Nat extend it, as in Kurt): Nat, Int, Rat are the sets of the embedded casts of ℕ, ℤ, ℚ, so - and / are the real ones everywhere, ^ is the real power Real.rpow, and n! is Γ(n + 1) (Real.Gamma: 0! = 1 and n! = n (n - 1)! for every n > 0, the two rules number.kurt has, and the factorial for a natural number). In analysis.kurt abs is |x|, sum i (a, b) T the sum of T(b), T(b-1), ..., T(b - k) for the k + 1 = ⌊b - a⌋ + 1 terms that are at least a, and 0 for a > b (the empty sum: "sum-empty"; "sum-last" is for a <= b + 1), max/sup the supremum sSup of the values (min/inf: sInf), argmax a choice (Hilbert's ε), lim and tends Mathlib's limit along the punctured neighbourhoods; in continuity.kurt and derivative.kurt cont, diff, deriv are ContinuousAt, DifferentiableAt, deriv; in sequences.kurt converges and seqlim the limit along atTop of the values at 0, 1, 2, ...; in integral.kurt integral is Mathlib's interval integral and integrable is read as "continuous on [a, b]" (the rules make a function integrable only that way).

    complex.kurt reads complex as Mathlib's ℂ (lean complex ℂ): a real where a complex number is required is its cast ((x : ℝ) : ℂ), z + x is the + of ℂ and x + 1 of reals the one of ℝ, i is Complex.I, re, im, conj, cabs are Complex.re, Complex.im, starRingEnd ℂ, ‖z‖. Among the sets a real is the complex number it is: k_embC embeds a complex number with imaginary part 0 as its real part (k_emb), every other one at a von Neumann level above those of the reals (a definition, injective, nothing assumed), and Complex is the set of them. The complex ^ is k_cpow, the real power on two reals (^ is one function: a real power is a complex one) and Mathlib's cpow otherwise. A rule about complex numbers used for reals (complex-div-self for x / x = 1) is a statement about their casts, which Mathlib's casts bring back (norm_cast, push_cast).

    The theories' rules are theorems. A rule's proof in Lean is kept with the rule, in its theory:

    use $a = $b  ⇒  $a + $c = $b + $c   "add-eq"
lean "add-eq" intros; subst_vars; rfl

    lean "label" TACTIC is a line of a proof (a tactic, raw to the end of the line, ; too, so no comment after it; more lines for the same label are the next lines of the proof, an indentation after one space is kept) of the fact "label" of the file, at its top level and after the fact -- only output, as tex: Kurt doesn't read the tactic. kurt --lean writes such a rule as a theorem with this proof instead of an axiom (with a comment -- number.kurt:70 "add-eq": proved in Lean), so Lean checks the theory's rules, not only the steps of the proof; a tactic that doesn't prove the rule is an error in Lean. The rules a chain of Mathlib's relations generates (chain = <= <: "chain-trans-1-2") are theorems by linarith, as flat/sym of + are by ring, and what the calculator knows of Nat (6 ∈ Nat, k_calc_Nat) is one of k_mem_Nat; a def of a loaded file that a step uses is a Lean def, as the file's own. Every rule of the theories of numbers (number, natural, divisibility, analysis, continuity, sequences, derivative, integral) and of set.kurt is proved this way -- interval.kurt's six rules of {a, ..., c} and {a, b, ...} too (the sets of their shapes' lean) -- but "integral-riemann" (true for a continuous function, but its proof isn't in Mathlib); and the theorems Kurt proves in number.kurt, natural.kurt and divisibility.kurt have a lean "label" too, for a proof that cites them (those about ⊂, even, odd, ∣, coprime unfold the defs of these symbols). The tactics don't name the variables (intros, ‹_›): Kurt orders the arguments of +, * and ∧ its own way, and names its variables by numbers. kurt --lean number.kurt writes a theory itself, all its rules with their proofs.

    Where the proof's theories give a lean Obj, kurt --lean writes import Mathlib, abbrev Obj : Type 1 := ZFSet.{0} with the embedding instead of the opaque axiom Obj : Type, a number 2 as (2 : ℝ), a mapped symbol by its template (the others stay axioms), the laws of a mapped flat/sym operator as theorems (ring), and a calc step by norm_num (then simp, ring_nf, linarith, decide; for a fact that computes to the goal, the same on the fact and the goal) -- what none of them closes stays a sorry, which Lean reports. The last line Kurt prints is then lake env lean FILE, to run in a lake project with Mathlib. Kurt's repository has one, scripts/lean (Lean and Mathlib of the same version as scripts/lean-toolchain; neither Kurt nor pip install kurt-lang needs it):

    cd scripts/lean && lake exe cache get      # once: Mathlib's prebuilt files, ~5 GB in scripts/lean/.lake
python3 scripts/lean_check.py proof.lean   # Lean with Mathlib if the file imports it, else plain `lean`

    -o FILE writes the document (or the Lean file) to FILE instead of next to the proof, -o - to the standard output, for a pipe: kurt --lean proof.kurt -o - | lean --stdin, kurt --markdown proof.kurt -o - | pandoc -o proof.pdf. Then what Kurt says goes to the standard error, and a proof that doesn't check writes nothing (an error, exit status 1). With -o, one format per run (without it, --latex --lean writes both files).
